### 1-5. 측정 방법

가이드 10장을 따랐습니다.

- 각 설정을 **별도 프로세스**로 실행해 GPU 메모리 상태를 격리했습니다.
- epochs=4 로 학습 후 **1에포크(준비 시간 포함)를 제외**하고 2~4에포크 평균을 사용했습니다.
- 예: YOLO11n b24 의 에포크별 시간은 33.93 / 21.19 / 20.87 / 20.79 초 → 1에포크가 13초 더 깁니다. 이를 포함하면 비교가 왜곡됩니다.
- 한 번에 한 항목만 변경했습니다 (batch → workers → cache 순).
- 고정 조건: imgsz=640, AMP 켬, device=0, 사전학습 가중치, seed=0, patience=0.
- GPU 메모리는 `torch.cuda.max_memory_reserved()` 로 측정했습니다.

### 2-3. 왜 batch=16 이 권장값인가

![그림2](figs/fig2_memory.png)

세 가지 근거입니다.

**(1) 수익 체감이 16에서 시작합니다.**
8→16 구간이 전체 개선폭의 90%(-15.3%p / -16.9%p)를 담당합니다. 16→24 는 -1.6%p 뿐입니다.

**(2) 메모리 비용이 급격히 오릅니다.**
batch 16 은 3.15 GB, 24 는 4.62 GB 입니다. 1.6% 의 속도를 위해 메모리를 47% 더 씁니다.
RTX 4060 은 8.19 GB 이고 Windows 데스크톱이 상시 0.5~2 GB 를 씁니다. 브라우저·Docker 를 켠 상태에서 batch 24 는 합계 6.6 GB 수준이 되어 여유가 1.5 GB 밖에 남지 않습니다. **batch 16 은 같은 조건에서 약 3 GB 의 여유를 남깁니다.**

**(3) 24를 넘으면 이득이 사라집니다.**
YOLO11n 은 24에서 처리량이 꺾이고(160.2 → 159.6 → 156.5), 48에서는 batch 16 보다도 느립니다. batch 를 키워 얻는 이득은 **GPU 연산 유닛을 채우는 것**인데, 24에서 이미 다 찼기 때문입니다. 그 이후로는 메모리 대역폭과 메모리 관리 부담만 늘어납니다.

**batch 24 를 쓸 조건:** 학습 전용으로 브라우저·Docker 등을 모두 종료해 GPU 메모리를 비운 경우. 실측 최고 처리량입니다.
**batch 48 은 어떤 경우에도 권장하지 않습니다.** 두 모델 모두 더 느리고 메모리는 6.75~7.59 GB 로 OOM 경계입니다.

## 3. 실험 2 — workers (효과 없음)

![그림3](figs/fig3_workers.png)

YOLO11n, batch=24, cache 끔 조건입니다.

| workers | 에포크 평균 | img/s | 판정 |
|---:|---:|---:|---|
| 0 | 55.15초 | 60.9 | 2.6배 느림 — 워커 자체는 필수 |
| **4** | **20.95초** | **160.2** | 기본값으로 충분 |
| 8 | 21.22초 | 158.2 | 차이 +1.3% (개선 없음) |
| 12 | 21.24초 | 158.0 | 차이 +1.4% (개선 없음) |

YOLO26n(batch=32)에서도 동일했습니다: workers 4 → 23.82초, workers 8 → 23.89초.

### 이것이 알려주는 것 — 병목은 GPU 연산입니다

가이드 5장은 "이미지 준비가 늦어 GPU 가 기다리는 상황이라면 workers 를 늘렸을 때 효과가 있다"고 했습니다. **효과가 없었다는 것은 GPU 가 기다리고 있지 않다는 뜻입니다.**

이 결론은 가이드 10장이 제시한 판정 기준과도 맞습니다. 그리고 다음을 함의합니다.

- **workers 를 12까지 올리는 실험은 불필요합니다.** 4로 두고 RAM 을 아끼는 편이 낫습니다.
- **이미지 압축·디스크 캐시로는 학습이 빨라지지 않습니다.** 가이드 3장의 "파일이 작아져도 GPU 가 계산하는 픽셀 수는 같다"는 지적이 실측으로 확인됐습니다.
- 남은 개선 수단은 **모델 크기 축소, 해상도 축소, 더 빠른 GPU** 뿐입니다. 앞의 둘은 가이드 9장이 정확도 위험 때문에 보류를 권한 항목입니다.

## 4. 실험 3 — RAM 캐시 (권장하지 않음)

| 설정 | 결과 | 에포크 평균 |
|---|---|---:|
| batch=24, workers=4, cache=ram | **실패** | — |
| batch=24, workers=0, cache 끔 | 성공 | 55.15초 |
| batch=24, workers=0, cache=ram | 성공 | 48.57초 |

**실패 원인:** Windows 는 프로세스를 spawn 방식으로 만들기 때문에, RAM 에 올린 이미지 배열 전체를 워커 프로세스로 직렬화해 전달하려다 실패합니다.
오류: `_pickle.UnpicklingError: pickle data was truncated` → `OSError: [Errno 22] Invalid argument`.
소량 세트(3,356장 × 640×640×3 ≈ 4.1 GB)에서도 발생했습니다.

**우회해도 손해입니다.** workers=0 으로 내리면 RAM 캐시가 동작하지만(55.15 → 48.57초, -11.9%), workers=0 자체가 workers=4 대비 2.6배 느립니다. **최종 비교: workers=4 + 캐시 없음 20.95초 vs workers=0 + RAM 캐시 48.57초 — 캐시 쪽이 2.3배 느립니다.**

가이드 7장의 "RAM 32GB 에서 전체 세트 RAM 캐시는 적합하지 않다"는 결론에, **Windows 에서는 소량 세트에서도 쓸 수 없다**는 사실이 추가됩니다. 디스크 캐시도 같은 워커 구조를 쓰므로 기대하기 어렵고, 병목이 GPU 인 이상 효과도 없을 것입니다.

### 5-2. 정확도 (4에포크 조기 지표)

| YOLO26n (b32) | **0.6222** | **0.850** | 0.492 | 0.587 | **0.701** | **0.781** | **0.629** | **0.863** |

클래스별 재현율입니다. **YOLO26n 이 vinyl 에서 0.347 → 0.629 로 크게 앞섭니다.** 가이드 8장이 주의 깊게 보라고 지목한 battery(0.708→0.781)·general(0.798→0.863)에서도 YOLO26n 이 우세합니다. can 과 plastic 만 YOLO11n 이 앞섭니다.

> **해석 주의:** 4에포크 값입니다. 어느 모델이 최종적으로 더 정확한지 판정하는 근거가 아니라, **초기 수렴이 빠르다**는 관찰입니다. 에포크당 13.7% 느려도 더 적은 에포크로 목표에 도달하면 총 학습 시간은 역전될 수 있습니다. 이 판단에는 전체 학습(조기 종료 포함)이 필요합니다.

### 5-3. 선택 기준

| 상황 | 선택 |
|---|---|
| 설정 실험·반복 학습 | **YOLO11n** — 빠르고 메모리도 적게 씀 |
| 최종 모델, vinyl·battery 재현율 중요 | **YOLO26n** — 4에포크 시점에서 뚜렷하게 우세 |

### 7-1. 무엇이 문제였는가

| 클래스 | 조정 전 train/val/test | 문제 |

가이드 8장은 "battery·general·vinyl 클래스별 재현율도 확인해야 한다"고 지시합니다. **general 의 test 박스 38개로는 1개 검출 여부가 재현율을 ±2.6%p 움직여 확인 자체가 불가능했습니다.**

### 7-2. 어떻게 조정했는가

- 목표: 이미 정상이던 4개 클래스(paper·plastic·can·vinyl)가 따르던 **80 / 15 / 5**.
- **`split_group` 단위 이동.** 매니페스트의 이 필드는 동일 원본·유사 장면 묶음(총 31,442개)입니다. 개별 이미지만 옮기면 같은 장면이 train 과 val 에 나뉘어 성능이 부풀려집니다.
- **train → val/test 단방향.** 기존 val/test 는 건드리지 않았습니다.
- 다중 클래스 이미지 때문에 한 그룹 이동이 여러 클래스 수치를 동시에 바꾸므로, 초과 허용치 60장·초과 벌점을 둔 탐욕 알고리즘으로 그룹을 선택했습니다.
- 결과: **167개 그룹, 3,173쌍(이미지+라벨) 이동.**

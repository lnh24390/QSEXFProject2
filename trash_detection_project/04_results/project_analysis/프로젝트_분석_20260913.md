## 1. 핵심 판단

이 프로젝트는 **7종 쓰레기 객체의 검출·세그멘테이션 모델을 위한 데이터 준비, 학습, 평가, 결과 해석을 한곳에 모은 실험 프로젝트**다. 데이터 분할 이동 기록, CUDA 환경, 체크포인트, 에포크별 지표, 배경 오탐 평가까지 갖추고 있다. 이미 유의미한 모델과 결과를 확보했다.

반면 현재 가장 먼저 보완해야 할 것은 모델 크기가 아니라 **결론을 뒷받침하는 평가 설계와 기록의 정확성**이다. 클래스별 이미지 수는 잘 맞춰졌지만 출처·증강본·장면 분포는 분할마다 크게 다르다. 기존 보고서는 이 차이를 일부 경고하면서도 앞부분에서는 효과와 원인을 단정한다. 다음 실험의 우선순위를 잘못 정할 위험이 있다.

| 구분 | 판단 |
|---|---|
| 데이터 파일의 기본 무결성 | 전수 검사 범위에서 양호 |
| 알려진 원본 그룹의 분할 분리 | 두 데이터셋 모두 교차 그룹 0개 |
| 클래스 수량 균형 | 대체로 달성. 이미지 수 균형이며 객체 수·출처 균형과 다름 |
| 검출 대 세그 직접 우열 비교 | 현재 전체 test 점수만으로 결론 불가 |
| 배경 이미지의 독립적 효과 | 현재 실험에서는 모델 변경과 섞여 있어 분리 불가 |
| 해상도 실험 | 실제 측정은 존재하나 표본 추출 편향과 속도 해석을 수정해야 함 |
| 결과 기록 | 원본 CSV는 활용 가능. 보조 텍스트 로그에 잘못된 손실 열 이름 존재 |
| 다음 방향 | 평가 기준 고정 → 출처·오류 분석 → 같은 모델로 배경 효과 검증 → 필요한 개선만 실험 |

## 5. 가장 중요한 데이터 문제: 출처와 증강 분포

### 5.1 클래스 균형이 출처 균형을 보장하지 않는다

| 출처 | bbox train 이미지 | bbox val 이미지 | bbox test 이미지 |
|---|---:|---:|---:|
| `s1:reusable7` | 9,148 | 1,397 | 1,124 |
| `s2:provided_json_annotation` | 21,420 | 4,370 | 219 |
| `generated_general_augmentation` | 6,946 | 38 | 4 |
| `roboflow_battery_export` | 6,036 | 1 | 160 |
| `s2:cigwaste` | 199 | 1,400 | 400 |
| `s2:recybat24` | 1,089 | 1,439 | 300 |

특히 plastic의 객체 출처가 극단적으로 달라진다.

| bbox plastic | val | test |
|---|---:|---:|
| 전체 객체 | 2,495 | 829 |
| `s1:reusable7` 객체 | 1,060 (42.5%) | 802 (96.7%) |
| `s2:provided_json_annotation` 객체 | 1,262 (50.6%) | 0 |

따라서 plastic의 val 성능이 높고 test에서 낮아지는 현상을 ‘작은 물체 때문’ 하나로 설명할 수 없다. **출처별 일반화 차이를 먼저 분리해서 봐야 한다.** 이는 출처 차이가 성능 하락의 원인임을 확정했다는 뜻은 아니다. 크기·장면·라벨 스타일이 출처와 함께 달라지는지 확인해야 한다.

### 5.2 general·battery는 독립적인 학습 경험의 양을 따로 봐야 한다

- bbox train의 general 포함 이미지 8,000장 중 **6,946장(86.8%)**이 매니페스트에 생성 증강본으로 표시돼 있다.
- bbox train의 battery 포함 이미지 8,000장 중 **6,036장(75.5%)**은 `roboflow_battery_export` 출처다. 이 출처 전체가 생성 증강본이라는 뜻은 아니며, 내부 원본 관계 확인이 필요하다.
- seg test의 general 포함 이미지 500장 중 **413장(82.6%)**이 생성 증강본이다. bbox test에서는 **4장(0.8%)**이다.
- seg test의 general 객체 575개 중 **441개(76.7%)**가 생성 증강 출처다.

‘general도 10,000장’이라는 수량만으로 실제 촬영 장면의 다양성을 판단할 수 없다. 또한 검출·세그 general 성능을 직접 비교하면 평가 출처 차이가 학습 방식 차이처럼 보일 수 있다.

### 5.3 크기 문제는 후보 원인이지 단독 결론이 아니다

이번 전수 집계에서 bbox train의 plastic 객체는 13,752개이며, 그중 4,727개(34.4%)는 이미지 면적 1% 미만이다. 객체 수가 가장 많으면서 test AP는 낮고 작은 객체 비율도 높다. 그렇다고 ‘객체 수 불균형은 원인이 아니다’, ‘작은 객체가 실제 병목으로 확인됐다’고 단정하면 안 된다.

클래스 7개로 계산한 상관계수는 출처, 투명도, 라벨 품질, 객체 밀도와 뒤섞인다. 다음 분석은 **같은 클래스 안에서 출처×크기 구간별 AP·미검출률**을 비교해야 한다. 클래스 간 7개 점의 상관보다 직접적인 검증이 된다.

## 6. 세그 라벨: 4점 폴리곤을 불량으로 단정하지 말 것

전체 세그 폴리곤 90,423개 중 4점 폴리곤은 **6,678개(7.39%)**다. 기존 집계는 재현된다.

| 클래스 | 전체 폴리곤 | 4점 폴리곤 | 비율 |
|---|---:|---:|---:|
| paper | 12,616 | 4,002 | 31.72% |
| battery | 14,035 | 1,628 | 11.60% |
| vinyl | 13,520 | 756 | 5.59% |
| plastic | 17,076 | 190 | 1.11% |
| general | 11,257 | 85 | 0.76% |
| can | 11,151 | 14 | 0.13% |
| glass | 10,768 | 3 | 0.03% |

그러나 좌표를 더 확인하면 **서로 다른 x 2개·y 2개로 이루어진 정확한 축정렬 4꼭짓점 조합은 37개뿐**이다. 이 수치는 회전 사각형이나 반올림 오차가 있는 사각형을 포함하지 않는 엄격한 검사다.

결론은 ‘나머지는 정상’도 ‘37개는 불량’도 아니다. **꼭짓점 수 4라는 사실만으로 박스 변환·잘못된 외곽선이라고 판단할 수 없다는 것**이다. 실제 종이와 포장재는 네 꼭짓점으로 표현될 수 있고 회전된 물체도 있다.

필요한 후속 검사는 출처별 표본의 원본 이미지와 폴리곤을 겹쳐 보고, 외곽선의 잘림·과대 포함·누락을 분류하는 것이다. 의심 인스턴스 라벨만 삭제하고 물체 이미지를 남기면 그 물체가 배경으로 취급될 수 있으므로, 라벨 수정 또는 명시적 제외·ignore 정책을 적용해야 한다.

### 7.3 배경 오탐과 불확실성

동일한 배경 test 150장, confidence 0.25 이상인 검출이 하나라도 있으면 ‘오탐 이미지’로 센 결과다.

| 모델 | 오탐 이미지 | 관측 비율 | 참고용 95% Wilson 구간 |
|---|---:|---:|---:|
| bbox_yolo11n | 5/150 | 3.33% | 1.43~7.57% |
| bbox_yolo26s_nobg | 40/150 | 26.67% | 20.24~34.26% |
| seg_yolo11n | 1/150 | 0.67% | 0.12~3.68% |

구간은 이미지가 독립인 이항 표본이라는 단순 가정의 참고값이다. 세 모델이 같은 이미지를 평가하므로 모델 간 차이 검정에는 이미지별 대응 결과가 필요하다. 1건과 5건만으로 세그가 일반적으로 더 낫다고 결론내리기 어렵다. confidence 0.5에서 seg의 0/150도 실제 오탐률 0%의 보증은 아니다(같은 계산의 상한 약 2.50%).

현재 오탐 비율은 선별된 COCO 배경에 대한 수치다. 현장 CCTV, 컨베이어, 바닥, 반사체, 손·장갑, 가림 장면까지 대표하지 않는다. COCO에 목표 물체 라벨이 없다는 사실만으로 물체 자체가 없다고 보증할 수도 없다.

또한 mAP·P/R 요약과 confidence 0.25·0.5 고정 오탐 측정은 다른 평가 항목이다. 실제 운용 기준의 precision/recall은 해당 confidence로 따로 계산해야 한다.

## 8. 해상도 실험에서 발견한 표본 편향

[`02_training/baseline_training/imgsz_scan.py`](../../02_training/baseline_training/imgsz_scan.py)의 67행은 다음 방식으로 표본을 뽑는다.

```python
files = files[::max(1, len(files) // n)][:n]
```

전체 길이를 n으로 나눈 정수 간격만큼 순회하고 앞 n개를 잘라서, 끝 구간에는 선택 기회가 없다. 파일명이 출처와 원래 분할을 포함하므로 실제 출처 편향이 발생한다.

| 실험 표본 | 전체 val | 선택 수 | 마지막 선택 인덱스(0부터) | 끝부분 미포함 |
|---|---:|---:|---:|---:|
| bbox_yolo11n | 9,628 | 1,500 | 8,994 | 633 |
| bbox_yolo26s_nobg | 9,178 | 1,500 | 8,994 | 183 |
| seg_yolo11n | 9,629 | 1,500 | 8,994 | 634 |

- bbox의 두 표본은 val에 있는 `s3:provided_coco_bbox` **162장을 전부 제외**한다.
- bbox_yolo11n 표본의 battery 포함 이미지는 177장으로, 다른 클래스 약 238~251장보다 적다.
- seg의 같은 출처는 전체 val 172장 중 **2장만** 표본에 들어 있다.

해상도마다 같은 표본을 썼으므로 **해당 표본 안의 비교 자체는 의미가 있다.** 하지만 전체 val 또는 현장의 최적 해상도로 확대 해석하기에는 부족하다.

저해상도 저장 결과는 다음과 같다.

| imgsz | bbox 26s 박스 | bbox 11n 박스 | seg 11n 마스크 | bbox 26s 추론 ms/이미지 |
|---:|---:|---:|---:|---:|
| 640 | 0.8719 | 0.8422 | 0.8240 | 4.93 |
| 576 | 0.8667 | 0.8382 | 0.8190 | 4.07 |
| 512 | 0.8609 | 0.8297 | 0.8103 | 2.97 |
| 480 | 0.8581 | 0.8253 | 0.7988 | 2.70 |
| 416 | 0.8457 | 0.8136 | 0.7817 | 2.13 |

속도 로그의 **batch는 16**이다. 위 수치는 배치 처리에서 이미지당 평균 추론 시간이며, 카메라 프레임 한 장의 전체 응답 지연이나 학습 시간은 아니다. 전처리·후처리·I/O를 합친 시간도 아니다. Ultralytics의 검증은 batch, imgsz, conf 등 설정에 따라 달라지므로 평가 설정을 결과에 고정 기록해야 한다. [공식 검증 문서](https://docs.ultralytics.com/modes/val/)

‘480 추론 성능은 480 전이학습 성능의 하한이다’, ‘전이학습하면 반드시 더 낫다’는 기존 보고서의 표현도 성립하지 않는다. 새 학습의 성능은 데이터와 최적화에 따라 나빠질 수 있으며, 추론 크기 변경 결과가 재학습 결과의 수학적 하한은 아니다.

## 9. 분석 코드와 운영상 결함

### 9.1 P1: 손실 지표 이름과 값이 어긋남

위치: [`metrics_logger.py`](../../02_training/baseline_training/metrics_logger.py) 143~153행.

코드는 손실 딕셔너리의 앞 세 값을 꺼내 `box / cls / dfl`이라는 고정 머리글 아래 기록한다. 실제 세그 순서는 `box / seg / cls / dfl 또는 l1 / sem`이다.

| seg_yolo11n 첫 에포크 | 실제 CSV | metrics.txt 표시 |
|---|---:|---|
| box_loss | 0.57322 | box=0.5732, 정상 |
| seg_loss | 1.18001 | cls=1.1800, 잘못된 이름 |
| cls_loss | 1.71860 | dfl=1.7186, 잘못된 이름 |
| dfl_loss | 0.96122 | 누락 |

bbox_yolo26s의 세 번째 손실도 실제는 `l1_loss`인데 `dfl`로 표시된다. 손실 곡선의 과제 간 비교와 원인 해석을 틀리게 만들 수 있다. 학습 자체의 손실 계산을 바꾼 문제는 아니며 **보조 텍스트 기록 문제**다. 분석에는 원본 `results.csv`의 실제 열을 사용하고, 로거는 이름 기반으로 기록해야 한다.

### 9.2 P1: 재실행 시 기존 실험을 섞거나 덮어쓸 수 있음

위치: [`train.py`](../../02_training/baseline_training/train.py) 120~122행 및 로거의 쓰기 모드.

고정 run 이름과 `exist_ok=True`를 사용하고 신규 학습은 설정·metrics·summary를 다시 쓴다. 기존 `results.csv`와 그림, 오래된 완료 요약까지 남으면 신규 실행과 이전 실행의 증거가 섞일 위험이 있다. 현재 완료 CSV에 중복 에포크가 발견된 것은 아니지만, 재실행 경로가 안전하게 차단돼 있지는 않다.

대책은 새 학습마다 고유 experiment ID를 사용하고, resume일 때만 동일 run을 쓰는 것이다.

### 9.3 P1: dry-run이 복구 인벤토리를 덮어씀

위치: [`seg_rebalance.py`](../../02_training/dataset_preparation/seg_rebalance.py) 106행.

`--apply` 확인 전에 `seg_split_before.csv`를 쓰기 모드로 연다. 따라서 현재 상태에서 단순 분석 목적으로 재실행해도 기존 ‘조정 전 분할’ 인벤토리가 현재 상태로 교체될 수 있다. 이번 분석에서는 이 스크립트를 실행하지 않았다.

`apply_moves.py` 역시 실행 즉시 이동을 수행하고 로그를 쓰기 모드로 연다. 이미지 이동 후 라벨 이동이 실패하는 경우에 대한 트랜잭션·복구 처리가 없다. 일회성 도구를 반복 사용 도구로 간주해서는 안 된다.

### 9.4 P1: 기존 분할 검증기가 현재 배경 데이터에 맞지 않음

- `02_training/dataset_preparation/seg_verify.py` 31행은 모든 파일이 `images__...` 형식이라고 가정한다. `bg_coco_...`에서는 정규식 결과가 None이어서 실패한다.
- `02_training/dataset_preparation/verify_split.py`와 `seg_verify.py`는 총 이미지 수를 59,236으로 고정해 배경 추가 후의 정상 62,236장을 실패로 표시한다.
- bbox 매니페스트의 split은 최초 분할이다. 현재 폴더와 3,173개가 다르다. 현재 학습은 폴더를 사용하므로 이 자체가 학습 누수는 아니지만, 이후 매니페스트만 읽는 분석은 낡은 분할을 재현할 수 있다.

이번에는 현재 폴더를 기준으로 동작하는 독립 감사 스크립트를 사용했다.

### 9.5 P2: 실험 종료 상태와 평가 상태가 약함

- `compare_bg.py`는 완료 여부 없이 가중치 존재만 확인한다.
- `pipeline_after_seg.ps1`은 종료 코드를 로그에 남기지만 단계 성공을 강제하지 않고, 완료 요약 파일의 존재에 의존한다. 오래된 요약이 있으면 잘못된 상태 판단이 가능하다.
- `metrics_logger.py`는 `실행 에포크 < 최대 에포크`로만 조기 종료 여부를 판단한다. 실제 yolo26s 로그에는 **100에포크에서 EarlyStopping 발동 메시지**가 있지만 summary는 ‘조기 종료가 걸리지 않았다’고 쓴다. 100에포크를 수행한 사실과 조기 종료 조건이 발동한 사실은 동시에 참이다.
- `merge_resume_logs.py`는 `_raw`가 있으면 항상 그 파일을 읽는다. 학습 중 조기에 실행하고 이후 새 에포크가 생긴 경우 최신 기록을 반영하지 못할 수 있으므로 완료 후 사용 또는 원본 버전 검증이 필요하다.

### 9.6 P2: 재현성과 분석 확장성 부족

- 절대 경로와 import 시 GPU 확인 등으로 데이터 설정과 학습 실행이 강하게 결합돼 있다.
- `uv.lock`은 존재하지만 결과별 패키지·코드·가중치·데이터 목록 해시를 묶은 기록이 없다.
- `psutil`은 코드에서 직접 import하지만 프로젝트 직접 의존성에는 없다. 현재는 간접 설치돼 있다.
- TensorRT 등 수동 설치 이력은 문서에 있으나 프로젝트 선언과 실제 환경이 완전히 같은지는 별도 확인이 필요하다.
- 결과 CSV에서 mAP 열에 배경 오탐 이미지 수를 함께 넣는 혼합 구조는 후속 집계 실수를 유발한다.
- 이미지별 예측·정답 매칭과 대응 오탐 목록을 표준 결과로 저장하지 않아, 출처별 AP와 대응 bootstrap을 기존 요약만으로 복원할 수 없다.

### 9.7 환경과 속도 측정의 재현성

분석 당시 설치 환경은 Python 3.12 계열, Ultralytics **8.4.146**, torch **2.14.0+cu126**, torchvision **0.29.0+cu126**이다. 기존 학습 로그의 장비는 RTX 4060 약 8GB다.

| 완료 학습 | 저장된 총 학습/소요 시간 | 해석 |
|---|---|---|
| bbox_yolo11n | 13시간 18분 10초 | summary의 학습 시작 이후 소요 시간 |
| seg_yolo11n | 15시간 40분 8초 | 재개 구간 에포크 합, 중단 대기 제외 |
| bbox_yolo26s_nobg | 20시간 31분 30초 | summary의 학습 시작 이후 소요 시간 |

요약 시간은 최종 검증 포함 여부와 재개 기록 방식이 다를 수 있다. 엄밀한 비용 비교에는 에포크 시간 합, 초기 준비, 최종 검증, 중단 대기를 분리해야 한다.

`01_datasets/auxiliary/benchmark_subset`은 폴더 이름과 달리 실제 벤치마크 로그상 train 이미지가 **3,356장**이다. 이름의 1,000을 전체 학습 이미지 수로 읽으면 처리량과 예상 시간을 잘못 계산한다. 벤치마크는 첫 에포크를 제외하고 JSONL에 실패까지 기록하는 점이 좋다.

다만 `bench_run.py`의 img/s는 train 이미지 수를 **검증 포함 에포크 시간**으로 나눈 값이다. 순수 GPU forward 처리량이 아니며 검증 크기가 달라지면 영향을 받는다. 벤치마크는 deterministic=False, 정식 학습 기록은 deterministic=True여서 환경도 완전히 같지 않다. 4에포크 시험의 클래스 recall로 최종 모델 정확도를 추천하거나, 작은 workers 차이만으로 전체 파이프라인의 병목을 확정하는 것은 피해야 한다.

기존 보고서의 낮은 lr0 전이학습 예제도 `optimizer=auto`를 유지하면 의도한 학습률이 적용되지 않을 수 있다. 실제 프로젝트 로그에 자동 optimizer가 lr0·momentum을 무시한다는 메시지가 있다. 새 실험에서는 실제 선택된 optimizer와 실제 lr을 기록해야 한다. [공식 학습 문서](https://docs.ultralytics.com/modes/train/)

## 10. 기존 보고서에서 정정해야 할 핵심 문장

대상: [`FINAL_REPORT_20260912.md`](../best_train/runs/FINAL_REPORT_20260912.md). 원문은 보존했다.

| 기존 주장 | 분석 후 적절한 표현 |
|---|---|
| 배경 이미지 효과가 수치로 확인됐다 | 배경 포함 모델에서 낮은 오탐이 관측됐지만 모델 조건이 달라 독립 효과는 미확인 |
| 세그가 박스 검출에서도 더 좋다 | 서로 다른 test에서 세그의 박스 점수가 높게 관측됐으며 직접 우열 판단은 보류 |
| 4점 폴리곤은 잘못된 외곽선이다 | 4점은 검수 후보 조건일 뿐 불량 라벨 판정이 아님 |
| test가 val보다 어렵다 | test 점수가 낮고 출처 분포가 다름. 원인별 평가가 필요 |
| 클래스 불균형은 10배 이상일 때 문제다 | 보편적인 10배 기준은 사용할 수 없음. 클래스 내 출처·난이도·원본 다양성을 함께 봐야 함 |
| 해상도 실험으로 작은 물체 병목이 확인됐다 | 편향된 val 표본에서 클래스별 반응이 관측됨. 객체 크기별 직접 검증 필요 |
| 480 추론 점수는 전이학습 점수의 하한이다 | 현재 가중치의 저해상도 추론 결과일 뿐 재학습 성능은 미측정 |
| 60에포크로 줄이면 기존 60에포크 성능을 얻는다 | 총 epochs 변경은 학습률 일정과 mosaic 종료 시점도 바꾸므로 별도 실험 필요 |
| batch·workers는 이미 최적, 병목은 GPU로 확정 | 해당 소량 벤치마크에서 workers 증가 이득이 작았음. 전체 학습과 다른 모델의 병목은 별도 측정 |

기존 보고서가 모든 곳에서 한계를 무시한 것은 아니다. 제한 사항이 뒤에 적혀 있지만 앞의 단정적인 결론과 모순된다. 최종 요약과 권고에도 같은 증거 수준을 적용해야 한다.

## 11. 현 시점의 판단과 다음 작업

현재 결과는 폐기할 이유가 없다. **어떤 모델이 어떤 데이터에서 어떤 성능을 냈는지 보여주는 유효한 실험 기록**이다. 다만 배경 효과·과제 우열·실환경 성능의 증명으로 과도하게 확대해서는 안 된다.

다음 작업은 다음 순서가 적절하다.

1. 실험 상태·손실 열·표본 추출·검증 도구를 정비하고 기존 결과를 고정한다.
2. 출처×클래스×크기별 val 오류를 분석하고 실제 운용 목표를 정한다.
3. 같은 모델·같은 평가 목록으로 배경 포함 여부만 바꾸는 실험을 설계한다.
4. 의심 라벨은 실제 이미지와 대조해 수정한다.
5. 640 기준을 확보한 뒤 576·512 등 속도 후보를 별도 비교한다.
6. 선택이 끝나면 새로운 현장 holdout으로 최종 검증한다.

구체적인 실행 단계와 완료 조건은 [새로운 전략 문서](학습_개선전략_20260913.md)에 정리했다.
